# 路由与调度

## 1. 问题定义
托盘调拨不是纯库存优化，还涉及运输执行层。需要解决：
- 哪个来源仓发货
- 走哪条线路
- 用哪类车辆
- 是否多仓合并 / 多点配送

## 2. 为什么调拨推荐必须考虑运输层
如果只在库存层做“从 A 到 B”的建议，而不引入运输层约束，常会出现：
- 推荐量理论可行，但找不到合适车辆
- 能发出，但来不及到达
- 成本远高于紧急补货阈值
- 仓库在该时间窗无法装卸

因此路由与调度不是后置补充，而是推荐可信度的重要组成部分。

## 3. 基本约束
- 车辆容量
- 起点 / 终点限制
- 装卸时间窗
- 可行路线
- 司机 / 车辆服务区域
- 多站点顺序影响
- 仓库接货能力

## 4. 典型场景
### 4.1 单仓到单仓调拨
适合作为 MVP 起点，结构最简单。

### 4.2 多仓补一个缺口
需要比较多个来源仓的成本与时效。

### 4.3 一车多站
若一个车辆可顺路完成多个调拨任务，可提高装载率并降低空驶。

### 4.4 depot 到仓补货
适用于回收和再投放网络较成熟的区域，但需要明确 depot 的状态口径和出货能力。

### 4.5 仓到 depot 回流调拨
更偏运营回流优化，MVP 可先不作为主场景，但应保留扩展思路。

## 5. 场景优先级建议
从 MVP 控制范围角度，建议按以下顺序推进：
1. 仓到仓调拨
2. depot 到仓补货
3. 多来源补同一目标仓
4. 一车多站 / 拼车

这样可以避免首期被复杂运输组合拖慢交付。

## 6. 算法思路
### 6.1 MVP
先以固定线路成本表 + 简单运力约束为主，不直接解复杂 VRP。

MVP 下建议把运输层拆成三个计算步骤：
1. **lane 可行性判断**：该来源到目标是否存在可用线路。
2. **ETA 估算**：根据标准时长、班次、发车截点、装卸时长，估计最早到达时间。
3. **运输成本估算**：按固定价、里程价、车型价或最低起运规则计算单位成本。

### 6.2 第二阶段
若存在较多多站点运输，可引入 VRP with Time Windows。

### 6.3 与优化模型关系
可分层求解：
1. 上层决定调多少、从哪到哪
2. 下层决定具体车辆与路线执行

### 6.4 MVP 推荐的 ETA 估算口径
建议采用：
`eta = max(now, next_available_departure_time, warehouse_ready_time) + loading_duration + lane_duration + unloading_duration`

其中：
- `next_available_departure_time`：下一可发车时刻
- `warehouse_ready_time`：仓库最早可出货时刻
- `lane_duration`：标准线路运输时长
- `loading_duration` / `unloading_duration`：装卸耗时

### 6.5 MVP 推荐的成本估算口径
建议先统一折算到“每次任务成本”和“每托盘成本”两个口径：
- `trip_cost = fixed_cost + distance_cost + toll_cost + special_surcharge`
- `cost_per_pallet = trip_cost / max(1, planned_qty)`

这样便于评分，也便于客户理解为什么同样补货量会有不同运输代价。

## 7. 路线与运力约束如何影响推荐
在 MVP 中，路线和运力至少会影响以下变量：
- 候选任务是否可行
- 最早可发车时间
- 预计到达时间
- 单位调拨成本
- 是否需要拆成多车次
- 是否会因班次稀缺而降低优先级

因此即便不做复杂路径优化，也必须把运输约束显式进入评分和解释。

### 7.1 运输层形式化符号建议
- `i`：来源节点
- `j`：目标节点
- `k`：车辆或车辆类型
- `t`：计划发车时点
- `lane(i,j)`：来源到目标的候选线路
- `cap_k`：车辆 `k` 的托盘容量
- `dur_(i,j,k)`：车辆 `k` 在 lane `(i,j)` 上的运输时长
- `cost_(i,j,k)`：车辆 `k` 在 lane `(i,j)` 上的单次运输成本
- `eta_(i,j,k,t)`：若在 `t` 发车时的预计到达时间

### 7.2 单任务运输可行性表达
对于候选任务 `(i,j,p,t)`，至少需满足：
- `x_(i,j,p,t) <= cap_k`
- `eta_(i,j,k,t) <= latest_acceptable_arrival_(j,p,t)`
- `lane(i,j)` 可用
- `warehouse_ready_time_i <= t`
- `receiver_available_time_j <= eta_(i,j,k,t)`

若以上条件不满足，则该候选任务应被过滤或重罚。

### 7.3 多车次拆分的最小表达
若 `x_(i,j,p,t) > cap_k`，则理论上需要：
`n_trips = ceil(x_(i,j,p,t) / cap_k)`

MVP 阶段可不解复杂多车协同，但至少要把：
- 需要拆车次
- 额外成本
- 可能延迟

显式反馈给审批人。

## 8. 调度输出建议
每条建议包含：
- 来源仓
- 目标仓 / 客户
- 托盘数量
- 建议发车时间
- 预计到达时间
- 建议路线或 lane
- 建议车辆或车辆类型
- 预计成本
- 风险标签

### 8.1 推荐增加的运输解释字段
为了方便审批与复盘，建议增加：
- `eta_confidence`
- `capacity_utilization_ratio`
- `trip_cost`
- `cost_per_pallet`
- `departure_cutoff_hit`
- `requires_manual_dispatch`

### 8.2 ETA 可信度分级建议
- `high`：有稳定 lane 时长 + 结构化班次 + 结构化装卸时长
- `medium`：有 lane 时长，但班次或装卸时长采用默认值
- `low`：仅按距离或经验规则估算

ETA 可信度低时，不宜把推荐包装成强承诺。

## 9. 风险标签建议
推荐结果中可增加以下风险标签：
- `tight_time_window`
- `high_transport_cost`
- `limited_vehicle_capacity`
- `source_risk_after_transfer`
- `stale_inventory_snapshot`

这些标签有助于审批人快速判断是否需要人工介入。

### 9.1 风险标签的半形式化判定示例
建议把风险标签和规则阈值挂钩，而不是纯人工主观判断，例如：
- `tight_time_window`：`eta` 距离最晚可接受到达时间小于阈值
- `high_transport_cost`：`cost_per_pallet` 高于区域中位数或合同阈值
- `limited_vehicle_capacity`：建议量接近或超过可用车辆容量上限
- `source_risk_after_transfer`：来源仓调出后 `post_transfer_expected_supply` 接近保护线
- `stale_inventory_snapshot`：库存快照时间距离当前时间超过阈值

### 9.2 为什么风险标签也要 formal 化
因为若风险标签没有规则口径，后续会出现：
- 同样场景不同调度员理解不同
- 客户无法验证系统逻辑
- 很难做 A/B 对比和复盘

因此即使 MVP 不做复杂概率建模，也应至少做到“规则阈值明确”。

## 10. 现实中的难点
- 运力并非完全可控
- 运输成本可能随时变动
- 一些路线的准时性不稳定
- 仓库作业能力会影响实际可执行性
- 第三方承运商反馈可能滞后

## 11. MVP 边界建议
首期建议只做：
- 多仓供需匹配
- 固定成本 lane 选择
- 单次调拨建议
- 简单车辆容量与时间窗校验

暂不强求全自动最优路径。

## 12. 失败与降级策略
- 若没有结构化路线成本表，则先按距离或人工维护成本表降级
- 若没有单车数据，则先按车辆类型能力估算
- 若预计到达时间无法可靠计算，则只输出来源仓优先级，不输出正式调拨建议

## 13. 对客户的可解释说法
建议把本模块解释为：
- 不是要替代 TMS 做完整路径求解
- 而是让调拨建议从“库存上可行”进一步提升到“运输上基本可行”

这样能更好控制客户预期，也更符合当前 MVP 范围。

## 14. 待客户确认
- 当前运力是否自营、外包还是混合
- 是否已有结构化路线成本表
- 是否需要支持多站拼车
- 调度频率是日计划还是小时级滚动
- 首期是否只支持仓到仓调拨
