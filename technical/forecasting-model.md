# 需求预测模型

## 1. 目标
在未来指定时间窗内，预测每个客户 / 仓库 / 区域的托盘需求量、需求发生时间和不确定性区间，为调度提供前置输入。

更准确地说，MVP 预测模块要优先回答两个问题：
1. 哪些节点在未来 1~7 天内可能出现明显需求上升或缺口风险。
2. 这些需求变化是否足以触发提前调拨。

## 2. 为什么先预测“聚合需求”而不是“逐单需求”
MVP 优先做聚合需求预测，而不是实时逐单预测，原因是：
- 当前文档阶段更强调可落地与可解释
- 客户实际可提供的数据常常先是订单汇总或计划汇总
- 调拨推荐更依赖时间窗内的总体缺口，而不是单笔订单的精确拟合
- 聚合粒度更适合快速回测和客户确认

因此，本阶段预测对象优先按“区域 / 仓库 + 托盘类型 + 时间窗”来定义。

## 3. 预测粒度
建议从简单粒度起步：
- 日级 / 周级
- 仓库级或区域级
- 托盘类型级

后续再逐步细化到客户级。

### 3.1 MVP 推荐主粒度
优先使用：
- `region_code + location_id + pallet_type + day`

### 3.2 数据不足时的退化粒度
若试点范围较小或历史样本不足，可退化为：
- `region_code + pallet_type + day`

然后再按历史占比或业务规则分摊到节点。

## 4. 预测标签定义
### 4.1 基本标签
- `predicted_demand`：未来某个时间窗内该节点对指定托盘类型的需求量

### 4.2 标签来源
通常由 `order_demand` 聚合形成：
- 按窗口聚合后的 `demand_qty`
- 过滤掉不应进入训练的无效状态

### 4.3 为什么标签要和调拨窗口一致
如果预测窗口和调拨窗口口径不一致，会导致：
- 预测说缺，调拨算不缺
- 预测说不缺，执行时却来不及补

因此预测输出必须服务于后续缺口识别和调拨规划窗口。

## 5. 输入数据
- 历史订单量
- 历史出库时间
- 客户属性
- 区域属性
- 托盘类型
- 季节性特征
- 节假日 / 促销日历
- 可选外部变量：天气、行业活动、零售促销周期

## 6. 分层建模思路
### 6.1 按区域分层
不同区域需求波动、回流效率和客户结构差异大，适合先做区域切分。

### 6.2 按托盘类型分层
不同托盘类型的周转节奏和需求模式不同，不建议混在同一个标签序列里直接训练。

### 6.3 按节点密度分层
高频节点可做独立预测；低频节点可先挂靠到区域级模型，再按规则分解。

这种分层能减少“全局单模型被局部稀疏数据拖垮”的问题。

## 7. 特征设计
### 7.1 时间特征
- day of week
- week of year
- month
- holiday flag
- moving average
- lag features

### 7.2 业务特征
- 客户类型 / 行业
- 仓库所属区域
- 托盘类型
- 历史回流滞后模式
- 服务等级 / SLA

### 7.3 扩展特征
- 气温 / 降雨
- 促销活动强度
- 节前备货效应
- 大客户专项活动计划

### 7.4 为什么保留库存辅助特征
库存不是需求标签本身，但可以帮助识别历史异常，例如：
- 因缺货导致的被压抑需求
- 因临时调拨导致的非常规出货峰值

## 8. 输出
- 某时间窗需求量预测值
- 上下置信区间
- 需求异常概率或风险标记
- 模型版本和生成时间

### 8.1 输出主键建议
为了让预测结果可回溯、可回测、可被调拨模块稳定消费，建议输出主键至少包含：
- `run_id`
- `model_version`
- `region_code`
- `location_id`
- `pallet_type`
- `window_start_time`
- `window_end_time`
- `time_granularity`

### 8.2 输出字段建议
除预测值本身外，建议同步输出：
- `baseline_value`：本次对比基线值
- `prediction_interval_width`：区间宽度，用于衡量不确定性
- `reliability_level`：如 `high` / `medium` / `low`
- `feature_snapshot_ref`：特征快照引用或批次号
- `generated_at`

### 8.3 为什么要显式输出可靠性等级
因为同样的预测值，在以下场景中的业务可信度不同：
- 历史样本充足且波动稳定
- 历史样本很少
- 最近出现异常大单
- 关键外部特征缺失

因此系统不应只输出一个数，还应输出“这个数值能信到什么程度”。

## 9. 第一阶段算法建议
不建议一开始上复杂深度学习。MVP 可优先比较：
1. 移动平均 / 周期规则
2. 季节性基线
3. LightGBM
4. XGBoost

原因：
- 可解释性更强
- 对小中型数据集更稳
- 上线与维护成本更低
- 更适合在文档与实施阶段形成清晰口径

### 9.1 形式化符号定义
为了统一预测、缺口识别与调拨输入口径，建议使用以下符号：
- `l`：位置节点（location）
- `r`：区域（region）
- `p`：托盘类型（pallet type）
- `t`：预测切点或时间索引
- `h`：预测窗口长度（horizon）
- `y_(l,p,t)`：节点 `l` 在时间 `t` 的真实需求量
- `x_(l,p,t)`：在时间 `t` 可观测到的特征向量
- `ŷ_(l,p,t+h)`：对未来窗口的预测需求
- `[L_(l,p,t+h), U_(l,p,t+h)]`：预测区间下界和上界

### 9.2 预测函数表达
MVP 可把预测问题统一写为：
`ŷ_(l,p,t+h) = f_p(x_(l,p,t))`

其中：
- `f_p` 可以是按托盘类型分层训练的模型
- 若样本足够，也可进一步细分为 `f_(r,p)` 或 `f_(l,p)`
- 当节点数据不足时，允许退化到更高层级模型

### 9.3 训练目标表达
对回归模型，可用经验风险最小化表达：
`min_f Σ w_(l,p,t) * Loss(y_(l,p,t+h), ŷ_(l,p,t+h))`

其中：
- `Loss` 在 MVP 中可采用 MAE 或加权绝对误差
- `w_(l,p,t)` 可用于提高高优先级节点、峰值样本、异常周样本的权重

### 9.4 为什么推荐先用加权绝对误差
因为本项目更关心：
- 大缺口是否被提前发现
- 峰值周是否被低估
- 高优先级节点是否持续失真

相比单纯最小化平方误差，适度加权的绝对误差更符合业务目标。

## 10. 训练样本构造
### 10.1 样本单位
每一条样本可理解为：
- 一个节点
- 一种托盘类型
- 一个历史时间窗
- 对应一个需求标签

### 10.2 样本构造原则
- 统一时间窗口径
- 补全无需求天，避免只看到非零需求
- 过滤明显无效状态和重复订单
- 将静态主数据与动态需求事实关联

### 10.3 为什么要补零样本
如果只保留有订单的日期，会高估平均需求，也会让模型误以为需求总在持续发生。

### 10.4 推荐训练样本表结构
建议形成统一的 `forecast_training_dataset` 视图或中间表，至少包含：
- `sample_date`
- `region_code`
- `location_id`
- `pallet_type`
- `target_demand_qty`
- `lag_1d` / `lag_7d`
- `rolling_mean_7d`
- `rolling_sum_14d`
- `dow`
- `week_of_year`
- `holiday_flag`
- `available_qty_snapshot`
- `available_soon_qty_snapshot`
- `service_level`
- `customer_mix_tag`
- `is_abnormal_sample`

### 10.5 标签泄漏提醒
以下字段若取值时点错误，容易导致训练时“偷看未来”：
- 未来窗口内才会确认的入库量
- 预测窗口之后才更新的库存快照
- 人工调度后的结果字段
- 事后修正过的需求事实

因此所有特征必须明确取自预测切点之前。

## 11. 评估方式
- MAE / RMSE
- MAPE（需注意低值分母问题）
- WAPE
- Bias
- 缺口识别准确率
- 高峰需求捕捉能力

### 11.1 指标解释
- **MAE**：适合衡量平均绝对误差，业务直观。
- **RMSE**：对大误差更敏感，适合关注峰值偏差。
- **MAPE**：低需求场景容易失真，只能辅助看。
- **WAPE**：对整体运营视角更友好。
- **Bias**：用来发现模型是否长期高估或低估。
- **缺口识别准确率**：比纯技术指标更贴近本项目目标。

### 11.2 建议补充的形式化评估指标
可进一步统一定义：
- `MAE = (1/N) * Σ |y - ŷ|`
- `RMSE = sqrt((1/N) * Σ (y - ŷ)^2)`
- `WAPE = Σ |y - ŷ| / Σ |y|`
- `Bias = Σ (ŷ - y) / Σ |y|`

对于业务更关注的缺口识别，可定义：
- 若 `gap_true > 0` 视为真实缺口
- 若 `gap_pred > 0` 视为预测缺口

则可进一步统计：
- 缺口召回率 Recall
- 缺口精确率 Precision
- 高风险缺口 F1

### 11.3 为什么要把预测评估和缺口评估拆开
因为一个模型可能在 MAE 上不错，但在业务上仍然失败，例如：
- 普通日预测很准，但高峰日总是低估
- 总量预测还行，但缺口节点总识别错

因此 LC 项目不能只看标准回归误差，还要单独看“是否识别出真正需要调拨的节点”。

## 12. 回测流程建议
- 采用滚动时间窗回测，而不是随机切分
- 至少覆盖最近 8~12 周
- 单独观察节假日前后、高峰周、大客户异常周
- 同时比较模型与规则基线

这一步的核心不是追求学术最优，而是让客户看到“模型是否比现有人工作法更稳定”。

## 13. 风险点
- 数据缺失或历史口径不一致
- 异常大单扰动模型
- 区域差异过大导致单模型失真
- 低频节点样本太少
- 节假日与促销影响没有被显式接入

## 14. 异常样本处理思路
建议将以下样本单独标记，而不是简单删除：
- 超大单或一次性项目订单
- 系统补录导致的时间异常
- 明显由库存缺货造成的异常低需求
- 节假日前后极端波动

保留异常标签，有助于后续：
- 训练时做加权或过滤
- 页面上解释预测风险
- 复盘“为什么这次预测偏差大”

## 15. MVP 建议
先做“区域 + 日级 + 托盘类型”的需求预测，再逐步下钻。不要一开始就做实时逐单预测。

## 16. 与缺口识别的衔接
预测模块的输出不是终点，真正业务动作来自：
- 预测需求
- 当前与近期供给
- 时间窗内已确认入库 / 回流
- 安全缓冲

因此，预测文档必须与缺口定义和调拨文档联动，不可孤立理解。

## 17. 降级策略
- 若节点历史数据不足，降级到区域级预测
- 若模型训练失败，降级到规则基线
- 若扩展特征缺失，退回只用时间和历史需求特征
- 若预测可靠性低，输出风险提示而不是强结论

## 18. MVP 范围提醒
首期目标是“可执行说明稿”，不是复杂算法平台设计：
- 不做深度学习时序模型
- 不做实时在线学习
- 不做复杂联合预测体系
- 先把对象、标签、样本、评估、降级逻辑说明清楚

## 19. 待客户确认
- 可提供多长历史数据
- 是否有可靠的节假日 / 促销标记
- 业务上接受的预测刷新频率
- 是否更看重总量准确还是峰值预警
- 是否需要人工修订预测结果入口
