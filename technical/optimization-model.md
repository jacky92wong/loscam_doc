# 优化模型

## 1. 目标
在已知当前库存状态与未来需求预测的基础上，生成跨仓调拨和资源分配方案。

对 MVP 来说，优化模块更准确的定位是：**把“缺口识别”转成“可执行推荐”**，而不是一步到位追求数学全局最优。

## 2. 决策变量
核心决策包括：
- 从仓库 A 调拨到仓库 / 客户 B 的托盘数量 `x(A,B,t)`
- 调拨发生时间 `t`
- 使用哪一辆车或哪类运力
- 是否延期满足需求
- 是否拆分需求到多次调拨

### 2.1 集合与索引
为便于后续 formal 化，建议统一使用以下集合：
- `S`：可作为来源的节点集合（source nodes）
- `D`：存在缺口的目标节点集合（demand / deficit nodes）
- `P`：托盘类型集合
- `T`：规划时间窗集合
- `K`：车辆或车辆类型集合
- `A`：可用 lane 集合，其中元素可写为 `(i,j)`

### 2.2 参数定义
建议至少定义以下参数：
- `g_(j,p,t)`：目标节点 `j` 在时间窗 `t` 的缺口量
- `m_(i,p,t)`：来源节点 `i` 在时间窗 `t` 的可调拨量
- `u_(j,p,t)`：目标节点 `j` 的最大可接收量或容量余量
- `c_(i,j,p,t)`：单位调拨成本
- `f_(i,j,k,t)`：选择车辆/车辆类型 `k` 时的固定任务成本
- `τ_(i,j,k,t)`：运输时长或 ETA 函数
- `b_(j,p,t)`：覆盖单位缺口的业务收益或服务收益
- `r_(i,j,p,t)`：来源风险或执行风险惩罚系数
- `q_min_(i,j,p,t)`：最小经济发运量
- `cap_k`：车辆 `k` 的容量上限
- `M`：大常数（仅在需要联立 0/1 变量时使用）

### 2.3 决策变量 formal 定义
- `x_(i,j,p,t) >= 0`：从来源 `i` 到目标 `j` 在时间窗 `t` 调拨的托盘数量
- `z_(i,j,p,t) ∈ {0,1}`：是否启用候选任务 `(i,j,p,t)`
- `y_(i,j,p,k,t) ∈ {0,1}`：是否由车辆/车型 `k` 执行候选任务
- `s_(j,p,t) >= 0`：未满足缺口的剩余量（shortage slack）
- `e_(i,p,t) >= 0`：来源仓超额调出的风险松弛量（仅当业务允许软约束时使用）

### 2.4 为什么需要 slack 变量
在真实业务里，经常出现“供给不够、成本太高、时间窗来不及”的情况。若模型只允许严格可行解，可能会得到无解；加入 `s_(j,p,t)` 后，可以把“无法满足的缺口”显式量化，并在目标函数中施加惩罚。

### 2.5 多时间窗扩展变量
当问题扩展到多时间窗 `T` 时，建议进一步补充：
- `I_(l,p,t)`：节点 `l` 在时间窗 `t` 结束时的可用库存状态
- `a_(l,p,t)`：在时间窗 `t` 内到达并可计入供给的入库量
- `d_(l,p,t)`：在时间窗 `t` 内实际发生的需求量或消耗量
- `h_(j,p,t) >= 0`：从窗口 `t` 延续到 `t+1` 的未满足缺口（carry-over shortage）
- `δ_(j,p,t) >= 0`：在窗口 `t` 被延期处理的缺口量

这样模型才能表达“这一窗没补完，会如何影响下一窗”。

## 3. 目标函数
总体目标可表述为：

最大化：
- 订单满足率
- 托盘利用率

最小化：
- 调拨成本
- 缺货惩罚
- 超容量惩罚
- 空驶惩罚
- 延迟惩罚

可用加权和形式实现：
`maximize service_score + utilization_score - transfer_cost - shortage_penalty - empty_mile_penalty - delay_penalty`

### 3.1 形式化符号定义
- `i`：来源节点
- `j`：目标节点
- `p`：托盘类型
- `t`：规划窗口或发运时点
- `x_(i,j,p,t)`：从 `i` 调拨到 `j` 的计划数量
- `g_(j,p,t)`：目标节点缺口量
- `m_(i,p,t)`：来源节点可调拨量
- `c_(i,j,p,t)`：单位调拨成本
- `τ_(i,j,t)`：运输时长或 ETA
- `z_(i,j,p,t)`：是否选择该候选任务的决策变量，可取 0/1

### 3.2 供需匹配层的目标函数表达
若先不显式建复杂路径变量，可将供需匹配层的目标写成：
`max Σ benefit_(j,p,t) * x_(i,j,p,t) - Σ c_(i,j,p,t) * x_(i,j,p,t) - Σ risk_(i,j,p,t) * x_(i,j,p,t)`

其中：
- `benefit_(j,p,t)` 表示填补目标缺口的收益
- `c_(i,j,p,t)` 表示运输与执行成本
- `risk_(i,j,p,t)` 表示来源仓风险、时间窗风险、执行不确定性

### 3.3 启发式评分与优化目标的对应关系
MVP 虽然不解严格全局最优，但打分函数本质上是在近似上述目标：
- 高缺口、高紧急度 → 提高 `benefit`
- 高成本、长距离、来源风险高 → 提高 `cost/risk`

因此启发式并不是“拍脑袋规则”，而是优化目标的工程化近似。

### 3.4 带 slack 的目标函数示例
若显式引入未满足缺口和来源风险松弛量，则可写为：
`max Σ_(i,j,p,t) [b_(j,p,t) - c_(i,j,p,t) - r_(i,j,p,t)] * x_(i,j,p,t) - Σ_(j,p,t) λ_short * s_(j,p,t) - Σ_(i,p,t) λ_source * e_(i,p,t)`

其中：
- `λ_short`：未满足缺口惩罚系数
- `λ_source`：突破来源保护线的惩罚系数

### 3.5 为什么 slack 惩罚比直接硬约束更灵活
因为在供应不足时：
- 硬约束模型可能直接无解
- 引入 `s_(j,p,t)` 后，模型会优先“少量违约”而不是整体失败

这更符合实际调度场景，也更便于向客户解释“系统已经尽力，但还有哪些缺口无法覆盖”。

### 3.6 多时间窗目标函数扩展
当引入多时间窗后，建议在目标中额外考虑：
- 延期惩罚
- 跨窗累积缺口惩罚
- 过早或过晚调拨造成的库存占用成本

可写成扩展形式：
`max Σ_[t] Σ_(i,j,p) [b_(j,p,t) - c_(i,j,p,t) - r_(i,j,p,t)] * x_(i,j,p,t) - Σ_[t] Σ_(j,p) λ_short * h_(j,p,t) - Σ_[t] Σ_(j,p) λ_defer * δ_(j,p,t) - Σ_[t] Σ_(i,p) λ_source * e_(i,p,t)`

其中：
- `h_(j,p,t)`：窗口结束时仍遗留的缺口
- `δ_(j,p,t)`：被显式延期的缺口量
- `λ_defer`：延期惩罚系数

### 3.7 为什么多时间窗下要单独处罚延期
因为“这窗没满足、下窗再说”和“永久满足不了”在业务上不是同一回事：
- 前者可能是可接受的运营折中
- 后者意味着持续服务失败

因此建议对延期与未满足设置不同惩罚，而不是混成一个缺口指标。

## 4. 为什么目标函数必须多目标
池化调度天然是多目标问题：
- 只优化服务水平，会过度调拨，成本过高
- 只优化成本，会牺牲高优先级需求
- 只优化利用率，会把风险外溢给来源仓

因此 MVP 即使采用启发式，也必须显式说明各评分项来自哪些业务目标。

## 5. 主要约束
### 5.1 库存约束
来源仓在任一时间窗内的可调拨数量不能超过真实可用库存。

建议进一步明确为：
`planned_transfer_qty <= movable_qty`

其中：
`movable_qty = available_qty + releasable_available_soon_qty - safety_buffer - reserved_qty_impact`

### 5.1.1 多时间窗下的 `movable_qty_(i,p,t)` 定义
当扩展到多时间窗后，建议按窗口定义：
`movable_qty_(i,p,t) = max(0, I_(i,p,t) + releasable_available_soon_qty_(i,p,t) + confirmed_inbound_qty_(i,p,t) - source_protection_threshold_(i,p,t) - reserved_qty_impact_(i,p,t))`

其中：
- `I_(i,p,t)`：窗口开始或窗口内可直接视为可用的库存
- `releasable_available_soon_qty_(i,p,t)`：在窗口 `t` 内预计可恢复可用的数量
- `confirmed_inbound_qty_(i,p,t)`：在窗口 `t` 内确认到达并可入供给的数量
- `source_protection_threshold_(i,p,t)`：来源仓在窗口 `t` 需要被保护的供给底线
- `reserved_qty_impact_(i,p,t)`：已被高优先级需求锁定的数量

### 5.1.2 为什么 `movable_qty` 不能只看当前 available
因为在多时间窗下，真正能拿去支援别人的量，不只取决于“现在有多少”，还取决于：
- 本窗口内会不会有回流 / 可用化
- 本窗口内会不会有确认到货
- 本仓未来近窗是否自己就会缺

所以 `movable_qty` 本质上是一个窗口化净可调拨量，而不是静态库存值。

### 5.2 可用时间约束
`available_soon` 托盘只能在其预计可用时间之后被使用。

### 5.2.1 `releasable_available_soon_qty_(l,p,t)` 的建议定义
建议将 `available_soon` 进一步拆成事件驱动的预计可用量：
`releasable_available_soon_qty_(l,p,t) = Σ q_e * 1(eta_available_e ∈ window_t) * confidence_e`

其中：
- `e`：一条预计恢复可用事件，例如回收、维修完成、清洗完成、IoT 状态修正
- `q_e`：该事件对应数量
- `eta_available_e`：预计恢复可用时间
- `confidence_e`：该恢复事件的可信度系数，可取 `[0,1]`

### 5.2.2 为什么建议引入 `confidence_e`
因为很多 `available_soon` 并不是硬承诺，而是估计值。
例如：
- 回收 ETA 可能延迟
- 维修完成时间可能变化
- IoT 修正可能还未被业务确认

若不打可信度折扣，多时间窗模型会系统性高估未来供给。

### 5.3 仓库容量约束
目标仓接收后不能超过容量上限或作业能力上限。

### 5.4 车辆容量约束
每辆车承载托盘数受容量约束。

### 5.5 时间窗约束
调拨需满足发车、到达、装卸和客户服务时间窗。

### 5.6 状态约束
维修中、损坏、丢失托盘不能进入可调拨集合。

### 5.7 路线约束
某些路线可能不可达、成本过高或班次受限。

### 5.8 来源仓保护约束
来源仓调出后，仍应满足本地安全缓冲和未来近窗需求。

可进一步表示为：
`post_transfer_expected_supply >= source_protection_threshold`

### 5.9 拆单约束
若业务不允许同一缺口由多个来源仓同时补货，则需增加：
- 单缺口单来源约束

若允许拆单，则需控制：
- 单缺口最大来源仓数
- 单缺口最小单次发运量

### 5.9.1 `source_protection_threshold_(i,p,t)` 的建议定义
建议不要把来源保护线写成固定常数，而应按窗口动态定义：
`source_protection_threshold_(i,p,t) = safety_buffer_(i,p,t) + protected_demand_(i,p,t,t+H) + risk_buffer_(i,p,t)`

其中：
- `safety_buffer_(i,p,t)`：基础安全库存
- `protected_demand_(i,p,t,t+H)`：来源仓在未来保护窗口 `H` 内自身需要优先保障的需求
- `risk_buffer_(i,p,t)`：用于吸收预测误差、回流延迟、IoT 不确定性的缓冲

### 5.9.2 为什么来源保护线必须是动态的
因为来源仓今天富余，不代表明天也富余。
如果保护线不随时间变化，系统就可能：
- 今天过度调出
- 明天自己出现紧急缺口
- 形成“拆东墙补西墙”的假优化

### 5.10 最小经济发运量约束
当调拨量过小时，运输固定成本会导致单位成本过高。建议增加：
`planned_transfer_qty >= min_economic_qty`

这样能避免系统推荐“只调 2 个托盘却跑一整车”的伪最优方案。

### 5.11 formal 约束组示例
若写成接近线性规划 / MILP 的形式，可表达为：

#### (1) 目标缺口平衡约束
对于每个 `(j,p,t)`：
`Σ_(i∈S) x_(i,j,p,t) + s_(j,p,t) = g_(j,p,t)`

表示：
- 调入量 + 未满足缺口 = 总缺口量

#### (2) 来源供给约束
对于每个 `(i,p,t)`：
`Σ_(j∈D) x_(i,j,p,t) <= m_(i,p,t)`

#### (3) 目标接收容量约束
对于每个 `(j,p,t)`：
`Σ_(i∈S) x_(i,j,p,t) <= u_(j,p,t)`

#### (4) lane 可用性约束
若 `(i,j) ∉ A`，则：
`x_(i,j,p,t) = 0`

#### (5) 启用变量联动约束
对于每个候选 `(i,j,p,t)`：
`x_(i,j,p,t) <= M * z_(i,j,p,t)`

表示：
- 若未启用该任务，则数量必须为 0

#### (6) 最小经济发运量联动约束
对于每个候选 `(i,j,p,t)`：
`x_(i,j,p,t) >= q_min_(i,j,p,t) * z_(i,j,p,t)`

表示：
- 一旦启用该任务，就不能发得过小

#### (7) 单任务单车型约束（MVP 可选）
对于每个 `(i,j,p,t)`：
`Σ_(k∈K) y_(i,j,p,k,t) = z_(i,j,p,t)`

#### (8) 车辆容量约束
对于每个 `(i,j,p,k,t)`：
`x_(i,j,p,t) <= cap_k + M * (1 - y_(i,j,p,k,t))`

#### (9) 来源仓保护软约束
对于每个 `(i,p,t)`：
`post_transfer_expected_supply_(i,p,t) + e_(i,p,t) >= source_protection_threshold_(i,p,t)`

若业务不允许突破保护线，则可移除 `e_(i,p,t)`，改成硬约束。

### 5.12 多时间窗库存平衡约束
若显式建模多时间窗，则对每个节点 `(l,p,t)` 建议增加库存递推：
`I_(l,p,t+1) = I_(l,p,t) + a_(l,p,t) + inbound_transfer_(l,p,t) - d_(l,p,t) - outbound_transfer_(l,p,t)`

其中：
- `inbound_transfer_(l,p,t)`：其他节点在窗口 `t` 调入到 `l` 且在该窗口内生效的数量
- `outbound_transfer_(l,p,t)`：节点 `l` 在窗口 `t` 调出的数量

这条约束是多时间窗模型的核心，因为它把当前决策和未来窗口连接起来。

### 5.13 carry-over shortage 递推
若允许缺口延期，则对每个 `(j,p,t)` 可写为：
`h_(j,p,t+1) = h_(j,p,t) + g_(j,p,t) - Σ_(i∈S) x_(i,j,p,t) - fulfilled_local_(j,p,t)`

或更简化地写为：
`h_(j,p,t+1) = δ_(j,p,t)`

表示：
- 本窗口未满足的缺口会滚入下一窗口

### 5.14 延期满足约束
若业务允许延期，可以增加：
`δ_(j,p,t) <= defer_limit_(j,p,t)`

并在目标函数中对 `δ_(j,p,t)` 加延期惩罚。

若某类客户或订单不允许延期，则直接令：
`δ_(j,p,t) = 0`

### 5.15 到货生效时间约束
跨窗调拨不能假设“发了就立刻可用”，建议增加：
- 只有当 `departure_time + τ_(i,j,k,t)` 落入窗口 `t'` 时，调拨量才计入 `a_(j,p,t')` 或 `inbound_transfer_(j,p,t')`

这一步是避免多时间窗模型高估未来供给的关键。

### 5.15.1 `confirmed_inbound_qty_(l,p,t)` 的建议定义
建议把确认在途量定义为：
`confirmed_inbound_qty_(l,p,t) = Σ q_s * 1(eta_arrival_s ∈ window_t) * confirm_flag_s * reliability_s`

其中：
- `s`：一条确认在途记录
- `q_s`：该记录数量
- `eta_arrival_s`：预计到达时间
- `confirm_flag_s`：是否已确认入库或运输承诺成立
- `reliability_s`：该在途记录可信度系数

### 5.15.2 `confirmed_inbound_qty` 与 `available_soon` 的区别
二者都影响未来供给，但语义不同：
- `available_soon` 更偏本地状态恢复
- `confirmed_inbound_qty` 更偏外部或在途补给到达

不建议把两者混成一个字段，否则难以解释未来供给到底来自哪里。

### 5.15.3 ETA 映射的实现建议
同一批在途量只能计入一个目标窗口，不应重复计入多个窗口。建议统一采用半开区间：
`eta_arrival_s ∈ [window_start_t, window_end_t)`

这样可以避免相邻时间窗重复计数。

### 5.15.4 `expected_supply_(l,p,t)` 的完整建议公式
在多时间窗下，建议统一定义：
`expected_supply_(l,p,t) = on_hand_available_(l,p,t) + releasable_available_soon_qty_(l,p,t) + confirmed_inbound_qty_(l,p,t) + inbound_transfer_(l,p,t) - reserved_qty_impact_(l,p,t) - blocked_qty_(l,p,t)`

其中：
- `on_hand_available_(l,p,t)`：窗口开始时已可立即使用的库存
- `releasable_available_soon_qty_(l,p,t)`：窗口内预计恢复可用的数量
- `confirmed_inbound_qty_(l,p,t)`：窗口内预计到达且被确认的在途入库量
- `inbound_transfer_(l,p,t)`：其他节点调入并在窗口内生效的量
- `reserved_qty_impact_(l,p,t)`：已被锁定或承诺给更高优先级需求的数量
- `blocked_qty_(l,p,t)`：虽然在账上存在，但因质量、状态、位置可信度不足而不可用的数量

### 5.15.5 为什么 `expected_supply` 里要扣 `blocked_qty`
因为在真实系统里，经常存在“账上有，但本窗口不能动”的库存，例如：
- 状态刚修正但尚未业务确认
- IoT 显示在场，但盘点未通过
- 处于待检、待清洗、待交接状态

若不扣这部分，系统会高估可执行供给。

### 5.15.6 `forecast_gap_(l,p,t)` 的完整建议公式
建议统一定义：
`forecast_gap_(l,p,t) = max(0, demand_requirement_(l,p,t) + carry_over_gap_(l,p,t) - expected_supply_(l,p,t))`

其中：
- `demand_requirement_(l,p,t)`：窗口 `t` 内需要满足的需求，可由已确认需求与预测需求组合得到
- `carry_over_gap_(l,p,t)`：上一窗口遗留的未满足缺口
- `expected_supply_(l,p,t)`：窗口 `t` 内可被系统信任并实际动用的供给

### 5.15.7 `demand_requirement_(l,p,t)` 的建议拆分
建议把需求要求量写成：
`demand_requirement_(l,p,t) = confirmed_demand_(l,p,t) + α * forecasted_demand_(l,p,t)`

其中：
- `confirmed_demand_(l,p,t)`：已确认订单 / 刚性需求
- `forecasted_demand_(l,p,t)`：模型预测需求
- `α`：预测需求折算系数，可按试点阶段调节

### 5.15.8 为什么建议引入 `α`
因为在很多客户现场，预测结果不应和确认订单拥有同等强度。
MVP 初期可用 `α < 1` 控制预测对调拨的影响，避免因为预测误差导致过度调拨。

## 6. 结果形式
优化结果不只是一个分数，而应包括：
- 建议调拨任务列表
- 每个任务的收益 / 成本解释
- 未满足需求列表
- 关键约束触发说明
- 降级或失败原因说明

### 6.1 推荐结果的最小字段
每条推荐任务至少建议包含：
- `plan_id`
- `task_id`
- `from_location_id`
- `to_location_id`
- `pallet_type`
- `planned_qty`
- `planned_departure_time`
- `planned_arrival_time`
- `lane_id`
- `vehicle_type` 或 `vehicle_id`
- `priority_score`
- `reason_codes`
- `status = pending_approval`

### 6.2 未满足需求输出
对于未覆盖缺口，必须输出未满足原因，避免业务误以为系统遗漏：
- `no_available_source`
- `source_protection_triggered`
- `lane_unavailable`
- `arrival_time_infeasible`
- `vehicle_capacity_insufficient`
- `target_capacity_blocked`

### 6.3 为什么未满足原因必须结构化
若只告诉客户“本次未推荐”，业务无法区分到底是：
- 真没库存
- 路线走不通
- 来源仓不能动
- 只是 ETA 不满足

结构化原因既能帮助审批，也能反向推动数据治理。

## 7. MVP 与后续阶段路线
### Phase 1：规则 + 启发式
按缺口优先级、距离、可用量、成本进行打分排序，快速给出建议。

### Phase 2：最小费用流 / 线性规划
在多仓供需网络下求更优流转方案。

### Phase 3：滚动时域优化 + VRP
结合时间窗与实际运输路线，持续滚动重算。

## 8. 为什么先从启发式开始
- 数据口径往往先不稳定
- 业务规则尚未完全固化
- 调度人员更需要可解释推荐而非黑盒结果
- 当前阶段是文档与实施说明，不是复杂求解器建设

## 9. MVP 与后续阶段边界
### 9.1 MVP 要做的
- 定义供给、缺口、可调拨量
- 建立候选任务生成逻辑
- 做硬约束过滤
- 做可解释加权评分
- 输出审批前推荐结果

### 9.2 MVP 明确不做的
- 全局最优求解器
- 多站点 VRP 细粒度路径编排
- 秒级实时自动重算
- 无人工审核的全自动执行

### 9.3 推荐的模型变体演进
为了控制范围，建议按建模复杂度逐步演进：

#### Variant A：单来源、单车型、单时间窗
特点：
- 每个缺口只允许一个来源仓
- 不区分具体车辆，只按统一容量上限
- 最适合首轮试点

#### Variant B：多来源、单车型、单时间窗
特点：
- 一个缺口可由多个来源共同补足
- 适合存在明显供给碎片化的区域
- 会引入拆单约束与最小发运量控制

#### Variant C：多来源、多车型、单时间窗
特点：
- 引入 `K` 集合和车辆容量差异
- 可更精细表达成本结构
- 但对车辆主数据完整性要求更高

#### Variant D：多来源、多车型、多时间窗
特点：
- 接近滚动时域优化
- 可显式处理延期、跨窗补货和动态供给
- 不建议在 MVP 首期直接落地

### 9.4 为什么要先把模型变体讲清楚
因为客户常会把“是否支持多来源、多车次、延期、跨天滚动”混在一起问。若没有变体分层，文档会不断膨胀，也难以控制交付范围。

## 10. 优化对象的层次
建议分为两层理解：
1. **供需匹配层**：决定从哪到哪、调多少。
2. **执行约束层**：决定能不能按时、按成本、按容量落地。

MVP 先把第一层做清楚，并让第二层提供可执行性过滤与评分影响。

### 10.1 两层模型的形式化理解
可将问题写成：

第一层（供需匹配层）：
- 在供给节点集合 `S` 与缺口节点集合 `D` 上分配流量 `x_(i,j,p,t)`
- 目标是尽量高收益地覆盖缺口

第二层（执行约束层）：
- 对已选候选任务验证 lane、车辆、ETA、容量、班次、装卸窗口
- 输出可行 / 不可行，以及执行成本修正

即：
1. `Matching Layer -> propose feasible transfer intents`
2. `Execution Layer -> validate and re-score transfer intents`

### 10.2 为什么分层比一步建模更适合 MVP
因为客户当前大概率面临：
- 数据口径还不稳定
- lane/vehicle 数据不完整
- 业务规则比求解器更重要

若一步建一个全局大模型，反而更难解释、也更难交付。

### 10.3 更正式的分层求解视角
可以把整体问题看成一个两阶段近似：

#### Stage A：Network Flow / Matching
输入：
- `g_(j,p,t)`
- `m_(i,p,t)`
- 基础 lane 成本
- 基础风险惩罚

输出：
- 一组候选流量 `x_(i,j,p,t)` 或任务意图

#### Stage B：Execution Feasibility Check
输入：
- Stage A 的候选任务
- 车辆/车型可用性
- ETA 规则
- 仓库装卸与接货窗口

输出：
- 可行任务
- 不可行原因
- 修正后的执行成本与优先级

### 10.4 启发式与 MILP 的关系
MVP 当前采用的“候选生成 + 打分 + 贪心选择”流程，可以理解为对上述 formal 模型的近似求解：
- 候选生成 ≈ 构造可行边集合
- 硬约束过滤 ≈ 先验可行域裁剪
- 打分函数 ≈ 目标函数局部化
- 贪心选择 ≈ 简化版启发式求解

这有助于后续从 MVP 平滑演进到：
- 最小费用流
- LP / MILP
- 滚动时域优化

### 10.5 多时间窗下的滚动优化理解
当引入多个时间窗后，建议按 rolling horizon 理解模型：
- 每次求解覆盖未来若干窗口，例如未来 3~7 天
- 只执行最近窗口或最近一批任务
- 新数据到来后重新求解后续窗口

这种方式比“一次性把未来全排死”更适合物流与托盘调拨场景。

## 11. 失败与降级策略
若优化输入不完整，不应强行输出高可信推荐，而应：
- 数据缺失时降级为风险预警
- 路线或运力缺失时只给来源仓排序建议
- 关键状态不可信时提示人工确认
- 预测缺失时不输出正式调拨任务

### 11.1 硬约束与软约束建议分类
为了避免模型无解或业务无法落地，建议把约束分为两类：

#### 硬约束（必须满足）
- 来源与目标不能相同
- 不存在 lane 则不可调拨
- `maintenance` / `lost` / `suspected_lost` 不可进入供给
- 目标仓容量不能被突破（若业务绝对禁止）
- ETA 超过硬性截止时间则不可执行

#### 软约束（允许违反，但需付惩罚）
- 来源仓保护线
- 最小经济发运量
- 服务时间窗边界附近的紧张任务
- 成本超出区域经验阈值
- 单缺口拆分来源数量偏多

### 11.2 为什么要区分硬软约束
如果所有约束都做成硬约束，模型容易无解；如果所有约束都做成软约束，又会产生业务上不可接受的方案。硬软分层是让模型既可求解又可控的关键。

## 12. 客户可读解释方式
建议对客户把优化结果解释成：
- 为什么这个目标仓被判定为高风险缺口
- 为什么这个来源仓适合支援
- 为什么这条路线在当前窗口内成本和时效更平衡
- 为什么某些缺口暂时未满足

这样才能把“优化”变成客户可验证的业务规则，而不是抽象数学模型。

### 12.1 惩罚系数设计原则
在 formal 模型中，`λ_short`、`λ_source` 等惩罚系数不能随意填写，建议遵循以下原则：

1. **服务优先场景**：`λ_short` 应显著高于一般运输成本，避免模型为了省运费而放任缺口。
2. **来源保护强场景**：`λ_source` 应足够高，防止为了救一个目标仓而把来源仓打穿。
3. **实验期先做量级校准**：先把收益、成本、风险都归一到同一数量级，再讨论业务偏好。
4. **不要一次引入过多惩罚项**：MVP 先保留 2~4 个核心惩罚项，避免参数过多导致不可解释。

### 12.2 推荐的调参顺序
建议先按以下顺序调：
1. `λ_short`：先决定“缺口容忍度”
2. `λ_source`：再决定“来源仓保护强度”
3. 运输成本权重：决定“省钱程度”
4. 时间窗 / ETA 风险权重：决定“时效敏感度”

这样更符合业务讨论逻辑。

### 12.3 启发式到 min-cost flow 的映射关系
当问题先不考虑复杂车辆与班次时，可把当前模型近似理解为一个带容量的最小费用流问题：
- 来源节点供给 = `m_(i,p,t)`
- 目标节点需求 = `g_(j,p,t)`
- 边容量 = 可行 lane / 目标容量 / 业务上限共同决定
- 边费用 = `c_(i,j,p,t) + r_(i,j,p,t) - b_(j,p,t)`

在这种视角下：
- 若只保留数量流，不保留 0/1 决策和复杂时间窗，问题可向 min-cost flow 靠近
- 若加入启用变量、车型选择、最小发运量等，则更接近 MILP

### 12.4 为什么这个映射有价值
因为它给了后续明确演进路径：
- MVP：启发式排序 + 贪心
- 中期：最小费用流
- 后期：MILP / 滚动时域优化 / VRP

也便于向客户解释“当前不是乱做，而是在沿着可升级的技术路线前进”。

## 13. 待客户确认
- 目标函数优先级如何排序
- 缺货惩罚是否有真实业务成本口径
- 是否允许延期或拆单
- 是否有固定调拨线路与合同运价
- 来源仓保护规则是否已有现成业务定义
